# architecture
- Background clicks must be delivered without bringing the target window to the foreground — the target window should never become visible, even across different macOS desktops. Confidence: 0.85
- Use https://github.com/trycua/cua and https://github.com/trycua/cua/blob/main/blog/inside-macos-window-internals.md as the authoritative reference sources for background click event logic on macOS. Confidence: 0.85
- Autoclicker must operate without interfering with the user's physical cursor — clicks are delivered to the target window independently while the user moves their cursor freely for other tasks. Confidence: 0.70
- For Chrome targeting, filter windows by name (e.g., "Google Chrome") via get_front_window_number rather than using find_window_at_point — Chrome's internal CursorUIViewService windows share the same PID and point-based lookup will pick them instead of the browser tab. Confidence: 0.70
- When stamping CGEvent fields for Chrome delivery, set field 7 (subtype) to 0 (NSEventSubtypeMouseEvent), not 3 (NSEventSubtypeTouch) — Chrome handles MOUSE_MOVED regardless of subtype but routes click events through the subtype-specific handler, and the touch path drops standalone events that aren't part of a began→moved→ended sequence. Confidence: 0.70
- On macOS 15, avoid CGEventPostToPid — it routes to the frontmost app regardless of the PID argument. CGEventPost(kCGHIDEventTap) with activate_without_raise delivers background clicks but also moves the physical cursor to the event's screen coordinates, even for click events (not just MOUSE_MOVED). The cursor movement is a side effect of posting any event through the HID tap. Confidence: 0.70
- On macOS 15, SLEventPostToPid (SkyLight private SPI) resolves successfully (function exists and can be called) but does not deliver click events — clicks silently fail with no error. Do not rely on it as a delivery path; it exists in the SkyLight framework but appears to be neutered on current macOS. Confidence: 0.75
